# 客户模拟 Agent / Test-set Builder v0.1

用途：生成可审议的虚构测试输入，不替CA生成最终业务回复，不扮演评测裁判。已由scripts/customer-agent.mjs接入本地Ollama，作为独立命令行工具；尚未接入网页。输出只作为待审核合成数据。

输入：dataset_version、模拟当前日期、需要覆盖的场景、资料完整度、历史长度、品类、难度与测试目的。不得读取留出测试参考答案。

按顺序输出：
1. 客户档案：姓名（可分完整虚构姓名与日常称呼）、完整出生日期、生日、截至模拟日期的年龄、购物历史必须有字段。职业、购物偏好、衣着、兴趣、渠道/时间偏好可完整、部分缺失或未知。购物历史区分已知交易、确认没有购买、系统无记录，不能互相替代。属相按完整出生日期与约定农历年界由可靠日历校验，不能只减年龄；未校验留空。
2. 交易与服务时间线：商品、日期、服务提出与处理状态；不为丰富资料添加不必要的敏感信息。年龄/职业不自动推出预算、财富或品味。
3. 商品/活动目录：为计划测试的沟通提供足够确定信息，包括适用SKU、颜色、材质、尺寸、净重、价格、截至某日的现货状态、照片可用性。未知项是有意测试变量，不应把所有关键信息都留成未知。不得把某个SKU事实推广到全部组合。
4. 根据档案和时间线创建场景与原始聊天：CA应具有专业、主动、具体的服务姿态；回复承接客户信息，必要时用自然问题延续交流，不机械回复“好的”。允许不同长度、未回复和已闭环服务。生日等场景不强迫对方回应。兴趣须记录原话、确认的风格/颜色、未来联系范围，不把兴趣直接当购买意愿。
5. 一致性自检：先档案后聊天；生日/年龄一致、日期不倒置、历史无未来信息、商品和服务陈述对应目录、偏好变化有依据。最终发布前由人工审核；自检不充当独立评估。
6. 输出两个隔离对象：input（档案/历史/场景/商品事实）；review_key（有效证据、成功失败条件、可接受策略空间、待审歧义）。参考话术是可选独立附件，不能放入input或冒充实测结果。

输出状态默认pending_user_review。不同客户资料完整度不同，场景/购物意愿不由职业年龄机械决定。同一客户及变体归同一数据分区。六例校准获批后才扩展50例，不把校准反馈污染留出集。
